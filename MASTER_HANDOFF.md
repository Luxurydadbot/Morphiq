## 2. What was built/fixed this session, in order

**Manual weight adjustment per set.** Added a +/- stepper next to the weight number on the active-set screen (WorkoutScreen.jsx), mirroring the existing reps stepper exactly. A member can now bump weight up or down for the set they're on without it being locked to the plan/AI-nudge value. The adjustment logs as the actual weight for that set (workout_logs, PR checks, the shared chat context) but never rewrites the plan itself — it resets to the plan/nudge weight on the next set, exercise swap, or AI swap, same as the reps stepper always did.

**Weekly progression made to actually reflect what was lifted — two passes, because the first one was incomplete.** Bryant asked directly: if he manually raises weight mid-set and hits good reps, does next week's target reflect that? It didn't — `progressPlan()` (shared.jsx) only ever checked reps against the plan's stale stored weight, then added the fixed increment to that same stale number. First fix based the bump on the higher of (plan weight, actual logged weight) — but that only ever helped when the member went heavier. Bryant then asked the reverse (coming back weaker after time off, manually lowering weight) — tested it directly and confirmed the "higher of the two" logic ignored a genuine drop entirely, plus separately surfaced a bigger problem: straight-set progression updates the flat `weight` field but never regenerates `setDetails`, the per-set table the workout screen actually renders (it prefers `setDetails` over the flat field whenever both exist) — meaning progression for `'same'`-style plans (the most common style AI-generated plans use) was silently invisible in the app regardless of whether the math was right. Final fix: removed the upward-only bias so next week's number comes from what was actually lifted in either direction, and both the straight-set and pyramid branches now regenerate `setDetails` on every weight change. Pyramid's existing 90%-of-plan-weight filter (used to isolate "top of the pyramid" sets) also got a tiered fallback, since a big manual drop could leave it with nothing above that stale threshold to base a new number on. Verified with 6 standalone test scenarios (raise/lower, success/fatigue/steady-state, both loading styles) run directly against the extracted function before pushing — not just "looks right."

**Weight-increment reference bug.** Both the new stepper and the pre-existing AI progressive-overload nudge read `plan?.progressionRule?.weightIncrementLbs` — but `progressionRule` is a plain description sentence (a string), so that lookup can never resolve and both were silently defaulting to a flat 5 lbs for every exercise, ignoring the per-exercise `weightIncrement` value the plan builder already sets. Fixed both to read `ex.weightIncrement` directly.

**Increment *sizing* itself was also wrong, not just the reference.** Bryant hit a real case: barbell incline press couldn't land on 135 (132.5 -> 137.5, skipping right past it). Root cause: `buildPlan()`'s `makeEx()` set `weightIncrement` by body region (squats/hinges = 5, everything else = 2.5) instead of by what's actually loadable. Researched how Strong/Hevy/StrongLifts handle this — they size the increment to the smallest real plate/dumbbell/pin jump, not body region, because a barbell press needs the identical 2.5-lb-per-side plate pair as a barbell squat. Changed the default to a flat 5 lbs for all equipment, and applied the same fix to `progressPlan()`'s legacy-plan fallback. Also corrected already-saved plan data directly in Supabase — both the flat `exercises` mirror and every day inside `customDays`, across all 4 existing profiles — so this took effect immediately without anyone needing to regenerate a plan. Kettlebells explicitly flagged as a separate, *unsolved* problem: they're fixed-size implements with uneven gaps between sizes, not a plate-based increment at all — left at 5 as a placeholder, not a real fix. Custom-plan creation (`CustomPlanScreen`) still hardcodes 2.5 for every new hand-built exercise regardless of equipment — intentionally not touched (see punch list #3).

**Gym branding bug — "IronForge Gym" showing instead of your real gym.** All 4 profiles in the database (both Bryant test rows, Greg's, one blank-named row) were set to `gym_id: 'demo-gym'`, which was never an actual row in the `gyms` table — so the app always silently fell back to the hardcoded "IronForge Gym" placeholder in `Morphiq.jsx`. Not a caching issue. Repointed all 4 profiles to `bryant-s-gym`, your real registered test gym. Bonus: this also resolved the long-standing "cafe75designs@gmail.com gym_id mismatch" item from prior sessions — that email turned out to belong to one of your own profiles, now fixed as part of the same correction.

**Discussed, explicitly deferred (no code changed):** exercise diagrams/animations (nothing exists today — would need a licensed clip/GIF library, one per movement pattern rather than per exercise variation, stored on the existing Supabase `exercises` table); screen information density (the word "warm-up" appearing four times on the active-set screen, general clutter) — Bryant explicitly flagged this for the aesthetics/redesign session rather than a quick fix now. Also did brief competitive research on the Ladder app at Bryant's request (video demonstrations as a standard feature, milestone badges, in-ear coaching cues) — informational only, logged as future ideas, no code changes.
