## Session 47, part 3 — built the weekly detection engine (weight-trend plateau + nutrition adherence), wired into both AI coach surfaces, live-verified end to end

Bryant asked to move on the weekly detection engine (Session 44's scoped-but-not-started feature): the AI coach noticing on its own when a member's weight trend has stalled or their eating has drifted off-plan, instead of only reacting to raw numbers when asked.

**Also resolved a loose end from earlier this session first:** Bryant said he's happy with `demo-gym`'s current blue accent color and wants the unused teal `accent_color` column gone. Cleared it directly via a database update (`gyms` table, `demo-gym` row, `accent_color` column only — set to null; `accent`, the column the app actually reads, was left untouched). Confirmed before and after with a direct query. Nothing in the app changed visually since that column was never read by any code path.

**Researched industry standards before building anything**, per Bryant's request to match "top 1%" practices rather than invent numbers. Findings (sources in this session's chat, not reproduced here): a weight-loss plateau is generally accepted as 3+ weeks of no real movement (1-2 weeks is normal noise); MacroFactor and WHOOP both compare smoothed multi-day trend averages, never a single day's raw number; WHOOP specifically layers multiple windows (7/14/30-day) and only calls something a real pattern when they agree, rather than using one flat cutoff — adopted that same layered-window approach here instead of the single-cutoff version first proposed. On nutrition: coaching platforms like Trainerize use a day-by-day pass/fail "compliance score," but MacroFactor deliberately avoids that ("adherence-neutral" philosophy) since it doesn't fit a no-guilt-language product — matched MacroFactor's approach instead of Trainerize's, since it's consistent with this app's own design rules.

**How it's built:**
- New file `src/coachSignals.js` (159 lines, pure functions, no React) — `computeWeightTrend()` and `computeNutritionAdherence()`. Kept out of shared.jsx on purpose since that file is already close to the 3,800-line hard limit (3,716 lines) — adding ~130 lines there would have crossed it.
- `computeWeightTrend()`: compares a 0-7 day average against 8-14 day and 15-28 day windows (weight_logs table, `weight_lbs`/`logged_date` columns). "Flat" = under 0.75% of body weight moved. Returns `plateau_confirmed` only when multiple windows agree, `plateau_possible` when only one does, `trending` for normal progress, `insufficient_data` when there isn't enough logging history to say anything (never guesses from sparse data).
- `computeNutritionAdherence()`: 7-day rolling average of logged calories (meal_logs table, `logged_cal`/`date` columns) vs. `plan.calories` (the member's real target — confirmed `user_settings.calorie_target` is unused dead weight nothing in the app reads, so didn't use it). Flags `off_track` only past 20% off target, and only when at least 3 days were actually logged that week.
- Both signals are computed once in `Morphiq.jsx`'s existing `loadHistoricalData()` (same place `weightChange` was already computed, no new database call, no new backend endpoint — stays under Vercel's 12-function Hobby cap) and stored on `historicalData`.
- Passed into `/api/coach-note` (the home-screen note, both call sites) and, via `ChatScreen.jsx` pulling `historicalData` from context, into `/api/chat` (the on-demand AI coach) — so if a member directly asks something like "why haven't I lost weight," the coach has the real answer instead of guessing from a single raw number.
- Both backend prompts (`api/coach-note.js`, `api/chat.js`) only mention the signal when there's actually something worth saying (`trending`/`on_track`/`insufficient_data` add nothing to the prompt) and are explicitly instructed to frame it as a suggestion, never guilt language — matches the design rule and the MacroFactor-style approach from the research above.

**Verification, done before calling this finished (not just code review):**
- Unit-tested both functions directly with synthetic data covering plateau, normal trend, sparse/insufficient data, off-track nutrition, on-track nutrition, and too-few-logged-days — all 7 cases returned the expected status.
- Hit the live production `/api/coach-note` endpoint twice with identical member data except for the trend/adherence signals: with `plateau_confirmed` + `off_track` the note correctly became *"Calories have been running about 600 over target lately — tightening that up will likely break the weight plateau."* With `trending` + `on_track` (everything else identical) the note was a normal completed-week message instead. Confirms the new context genuinely changes the AI's output, not just that the endpoint doesn't error.
- Hit the live production `/api/chat` endpoint with the question "why haven't I lost weight lately?" and the same plateau/off-track signals — got back an accurate, specific answer referencing the real numbers (*"your weight has been flat at around 180 lbs for several weeks, and your 7-day average calorie intake is coming in at about 2,400 calories — which is 600 calories above your 1,800 target"*) with a constructive next step, no guilt language.
- Confirmed no accidental changes to unrelated code: line-count deltas on every touched file were small and additive (Morphiq.jsx +13, ChatScreen.jsx +9, coach-note.js +23, chat.js +20), all existing try/catch blocks read back intact, `export default function Morphiq()` and the router untouched, esbuild syntax-checked all five touched/new files clean before pushing.
