## Session 44 — two real bugs fixed and shipped, push access re-escalated to Anthropic support, next feature scoped

**Bug 1 — cardio calorie math used a running-intensity MET value for walking.** Bryant's friend tested the cardio feature: 12 minutes of "moderate pace" treadmill walking logged as 295 calories, which isn't physically plausible. Root cause found in `src/CardioScreen.jsx`: the live-timer's `CARDIO_ACTIVITIES` list had one "Treadmill" entry hardcoded to `met: 9.8` — the standard exercise-science value for running roughly a 10-minute mile, not walking (real walking METs run 3-3.5). Every treadmill session, walk or run, was silently calculated at running intensity. **Fix:** split the single "Treadmill" entry into separate "Walk" (`met: 3.5`) and "Run" (`met: 9.8`, unchanged) options, added a matching walk icon to `ActivityIcon`. Confirmed with Bryant that his friend used the live timer (not the separate AI voice/text "log a past session" path), so this fix directly addresses what was reported. **Note for later:** the manual/voice logging path (`CardioQuickLog` → `api/parse-cardio.js`) estimates calories via a free-form AI guess and doesn't even receive the member's body weight — a separate, not-yet-addressed accuracy gap, flagged to Bryant but not scoped or actioned this session.

**Bug 2 — Home screen's nutrition macro bars crammed into thirds instead of stacked.** Bryant reviewed Session 43's four-macro nutrition work live and flagged that the Protein/Carbs/Fat bars on the Home "Nutrition today" card were laid out three-across (each a third of the card width), inconsistent with the full-width Calories bar directly above them. **Fix:** `MacroBar`'s `compact` mode (`src/shared.jsx`) redesigned from a centered 3-across layout to a label-left/value-right row with a full-width thin bar underneath, matching the Calories section's visual pattern. Container in `src/Morphiq.jsx` changed from a `flex` row to a `flex-column` stack. `compact` mode is only used in this one place (confirmed via grep before editing), so nothing else was affected.

**Vercel MCP connector.** Use `list_teams` → `list_projects` (project `morphiq`, id `prj_0KL9CirNTdNMnXEO34o3pdwd5wSM`, team `team_Iiv1x067TLmgX2XdP5mXO06v`) → `list_deployments` to check the `state` field (`READY` vs `ERROR`) of the most recent `production`-target deployment after every push, not just after a push that "feels risky." If `ERROR`, `get_deployment_build_logs` (`errorsOnly: true` for a quick read, but pull the full log too since the quick read may not show the actual compiler error text) points at the exact failing line. **Do not trust `esbuild` alone as a pre-push check** — it doesn't run ESLint, and this project's CRA build treats `react-hooks/rules-of-hooks` violations as a hard error (the many pre-existing `no-unused-vars`/`exhaustive-deps` warnings are not). When a change touches a hook in a component with an early return, run the real `npm run build` locally before pushing.

**`npm run build` behaves differently depending on `CI` environment variable — worth knowing.** Running it with `CI=true` set makes Create React App treat every ESLint warning as a hard build failure, including all the long-standing pre-existing warnings across this codebase. Running it plain (no `CI=true`), which matches how Vercel builds this project, compiles clean with warnings and exit code 0.

**WebFetch is not reliable for reading files from this repo — confirmed dangerous this session, see the project's "NETWORK ACCESS" notes for the full story.** Asked it to return HANDOFF.md verbatim and it fabricated a plausible-looking but entirely fictional "Session 10" handoff. Use `git clone` for any read where exact content matters (line counts, code, handoff docs) — confirmed reliable, matches real file contents exactly.

**Supabase MCP connector.** The app's own `sb_publishable_...` key (used by the running app itself) can only read/write rows in tables that already exist — it can never create or alter a table. When Bryant needs a new table going forward, use the official Supabase MCP tool (`apply_migration` for schema changes, `execute_sql` for one-off queries, `list_tables` with `verbose: true` to check real column names/types before writing app code against them, `get_advisors` after any DDL change) instead of asking Bryant to click through the dashboard by hand.

`profiles.supabase_user_id` is the auth link, `profiles.id` is the FK used everywhere else. The `exercises` table is still just a reference/classification table, not wired into live plan generation.

**esbuild remains useful as a fast first-pass syntax/JSX check** (`npx --yes esbuild <file> --outfile=/dev/null` — no `--loader` flag needed for files that already have a `.jsx` extension, esbuild infers it) but is not sufficient on its own before pushing hook-related changes — see the Vercel MCP note above. When `node_modules` isn't already present, `npm install --no-audit --no-fund` completes in well under 30 seconds in this sandbox.
