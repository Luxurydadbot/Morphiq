## Session 10 shipped

1. **Warm-up re-ramp bug fix.** Manually raising a warm-up set's weight (via the +/- stepper) used to log correctly for that one set, then get completely ignored — the next warm-up just replayed the original plan's number, which could even be *lower* than what was just lifted (e.g. raise 95→135, next warm-up shows 125). Root cause: warm-ups were a fixed, pre-computed ramp that never looked at what actually got logged, unlike working sets which already had this via `autoregulatedWeight()`. Fix: new `reRampWarmups()` in `shared.jsx` — backs out an "implied" working weight from the member's own number, then rebuilds every warm-up step after the overridden one proportionally off that, instead of flat-copying the number forward (which could flatten or invert the ramp). Wired into `WorkoutScreen.jsx` via a new `effectiveWarmups` computation that checks the most recently logged warm-up against the plan's original number for that step. Commit `127575c`.
2. **Warm-up adjustment messaging.** Two new UI moments, both reusing the existing `AINudgeCard` component (extended with a `message` prop) rather than inventing a new pattern: (a) bumping an *early* warm-up set shows a quiet reassurance note — "Warm-ups aren't meant to feel heavy — that's normal. Still ramping to X lbs" — since early warm-ups are supposed to feel light by design and reacting to that would be treating normal behavior as a problem; (b) bumping the *last* warm-up set (the real readiness check, closest to working weight) shows a real Accept/Keep prompt after logging — "That last warm-up looked strong — carry it into your working weight at X lbs?" — using a new `impliedWorkingWeight()` helper in `shared.jsx`. New `isLastWarmupSet` and `nudgeSource` ("overload" vs "warmupCarry") state in `WorkoutScreen.jsx` distinguish this from the existing progressive-overload nudge so both can share one card. Commit `6e7a227`.
3. **Out-of-range weight guardrail.** If a manually-adjusted set weight is ≥1.5x or ≤0.5x today's planned weight for that exact set (and the planned weight is at least 20 lbs, so tiny accessory numbers don't trigger noise), tapping "Log" now shows a confirm step first — "That's a big jump from today's plan — Planned X lbs, you've got Y lbs. Just checking that's right" — with "Let me adjust" / "Yes, that's right." Never blocks logging, just double-checks once. Deliberately rule-based, not an AI call — it's a plain number comparison, so it's instant, free, and gives the same answer every time; reserved AI for things that actually need language (chat, coach notes), not a range check. New `isBigWeightJump()` helper and `showBigJumpConfirm` state in `WorkoutScreen.jsx`, styled to match the existing amber warm-up-callout banner rather than a new visual pattern. Commit `e52c527`.

All three **live-tested end to end in Chrome** on a disposable test profile ("WarmupTest," still in Supabase — ask Bryant before removing). Confirmed: warm-up re-ramp climbs correctly from a manual override instead of reverting; early-bump reassurance text shows, last-bump prompt doesn't show early-bump text; last-warm-up carry prompt computed the exact right implied working weight (190 lbs warm-up → 225 lbs suggested working weight, matched by hand); guardrail fired on a +75 lb jump and stayed silent on a +10 lb jump (which also correctly triggered an unrelated genuine PR banner, confirming nothing else broke).

## Technical notes carried forward

GitHub REST API and raw.githubusercontent.com are blocked from the sandboxed shell — always `git clone`/`git push` over authenticated HTTPS. `profiles.supabase_user_id` is the auth link; `profiles.id` is the FK used everywhere else. Fire-and-forget `.catch(() => {})` pattern for all new Supabase writes. `AuthScreen` lives in `Morphiq.jsx`, not `shared.jsx`. The `exercises` table (91 rows: id, name, muscle_group, pattern, equipment, difficulty, variation_of, is_active) is a reference/classification table, still not wired into live plan generation — relevant for punch-list items THIRD (cardio, unrelated) and SIXTH, and for the deferred muscle-recovery-aware programming feature. Its `pattern` column (squat/hinge/push/pull/accessory) is tuned for exercise-substitution logic, not warm-up-need — `buildWarmupRamp()`/`reRampWarmups()` classify by exercise-name regex (`COMPOUND_LIFT_PATTERN`) instead, on purpose.

**Duplicate logic is the recurring root cause of real bugs in this codebase.** Both major session-9 bugs and the session-10 warm-up bug traced back to the same shape of mistake: two copies of near-identical logic living in different files or code paths, one gets fixed, the other doesn't, and they silently drift apart. When fixing something computed in more than one place, check for a second copy before considering it done, and prefer collapsing to one shared, exported function (`buildWarmupRamp()`, `reRampWarmups()`, `impliedWorkingWeight()`, `isBigWeightJump()` in `shared.jsx`/`WorkoutScreen.jsx` are the pattern to follow) over patching each copy separately.

**Watch for variable name collisions across the same file, even across different scopes.** Session 10 found a pre-existing `isLastWarmup` (pre-workout warm-up-exercise walkthrough step) that would have silently collided with a new same-named variable for "last warm-up *set* within an exercise." JS block-scoping means it wouldn't have caused a crash, but it's exactly the kind of thing that causes real confusion later — the new variable was renamed to `isLastWarmupSet` to stay unambiguous. Grep for a name before introducing it if it's at all generic.
